# Internationalization (i18n)

gemi's i18n is built around **component-scoped dictionaries**: a component declares the strings it needs, right next to itself, and a visitor downloads only the locale they are reading in.

## Dictionaries

Declare a dictionary with `defineDictionary`, in the component file or in a sibling file beside it. Each entry is a key mapping to a per-locale string:

```typescript
// app/views/Home.i18n.ts
import { defineDictionary } from "gemi/client";

export const homeDict = defineDictionary({
  title: {
    "en-US": "Welcome to Gemi {{version}}",
    "tr-TR": "Gemi'ye Hoş Geldiniz {{version}}",
  },
  description: {
    "en-US": "A simple and fast framework for building web applications.",
    "tr-TR": "Web uygulamaları oluşturmak için basit ve hızlı bir çerçeve.",
  },
});
```

```tsx
// app/views/Home.tsx
import { useDictionary } from "gemi/client";
import { homeDict } from "./Home.i18n";

export default function Home() {
  const t = useDictionary(homeDict);

  return (
    <div>
      <h1>{t("title", { version: "1.0" })}</h1>
      <p>{t("description")}</p>
    </div>
  );
}
```

That is the whole setup. There is no name string, no central `app/i18n/index.ts` to register in, no route-to-dictionary map to maintain, and no `gemi.d.ts` declaration — keys and interpolation params are inferred from the literal itself.

The **first locale is the source language**. A key missing from another locale falls back to it, so a half-translated dictionary degrades one string at a time rather than rendering the component as raw keys.

Inferred, but only where the inference is safe. The source language is the locale the first key lists first — which cannot move as long as **every key lists the same locale first**. Write your dictionaries `en-US` first and there is nothing to think about.

Where keys disagree, the build stops:

```
defineDictionary() cannot infer a source language. Key "onlyTurkish" lists
"tr-TR" first but "both" lists "en-US" first, so the locale every key falls
back to depends on the order they are written in — moving one key would
change what language a reader sees. Pass { sourceLocale: "<locale>" } as the
second argument to pin it.
```

Because that is exactly the case where a key added at the top re-points every other key's fallback, and nothing at runtime would notice. Pin it:

```ts
export const homeDict = defineDictionary(
  {
    onlyTurkish: { "tr-TR": "Merhaba" },
    both: { "en-US": "Hello", "tr-TR": "Merhaba" },
  },
  { sourceLocale: "en-US" },
);
```

`sourceLocale` is read at build time as well as at runtime, so it must be a string literal.

> **Why not take this from `defaultLocale`?** `translation.defaultLocale` answers a different question — which locale a visitor gets when detection fails, and which one has no URL prefix. A dictionary's source language is a property of how that file was authored, and the two can legitimately differ. More practically: the plugin bakes fallback order into each locale chunk at build time, while server code, jobs and tests read the same literal without ever meeting the bundler. A build-time-only default would make those two disagree, and `defineDictionary` is meant to behave identically either way.

### Only one locale ships

Every locale is written in one file, but gemi's Vite plugin rewrites the `defineDictionary` call at build time so each locale becomes its own chunk:

```js
// what the bundler actually emits
const homeDict = __gemi_dict__("d_f3cc5a4461dfa4b2", {
  "en-US": () => import("./en-US-BSyWTQsL.js"),
  "tr-TR": () => import("./tr-TR-o52Tzo3M.js"),
});
```

The strings leave the component's chunk entirely, and a visitor fetches one locale. In practice they rarely fetch anything: the server streams the strings it rendered with into the document, and the client router warms a view's dictionaries while it is already loading that view's chunks. The lazy `import()` is the fallback — it kicks in for a dictionary inside a `lazy()` subtree, or on the first render after a locale switch, where the component suspends until its strings arrive.

Because the literal is read at build time, it has to be **statically analysable**: an inline object of plain keys and string literals. A variable, a spread, a computed key, a template literal or a function value fails the build with the offending key named. (Use `{{param}}` interpolation instead of a template literal.)

`defineDictionary` also has to be **imported by name** — `import { defineDictionary } from "gemi/client"`. A namespace import (`gemi.defineDictionary(...)`) or a re-export through an app-local barrel cannot be traced back to gemi, so the plugin leaves that dictionary inline and warns at build time; every locale then ships to every visitor.

Nothing depends on the plugin for correctness. Untransformed — in `bun test`, or in server code that never meets the bundler — `defineDictionary` holds every locale and resolves synchronously. The plugin is purely the optimization.

### Interpolation

Strings support `{{param}}` placeholders, filled in at render time:

```typescript
title: {
  "en-US": "Welcome to Gemi {{version}}",
}
```

```tsx
t("title", { version: "1.0" }); // "Welcome to Gemi 1.0"
```

Placeholders also support **type casting** with `{{param:type}}` (`number`, `string`, `boolean`):

```typescript
"en-US": "You have {{count:number}} items";
```

And **interpolated content** with `{{param:[content]}}`, where the param is a function that receives the bracketed content — this is how you embed JSX (links, bold text) inside a translation:

```tsx
// "Read our {{terms:[terms of service]}} to continue"
t.jsx("notice", {
  terms: (label) => <a href="/terms">{label}</a>,
});
```

> **Note:** gemi has no dedicated pluralization API. Handle plurals with a `{{count:number}}` placeholder plus wording, a function param, or separate keys per plural form.

## Locale configuration

Locale settings live in the `translation` config slice — `app/config/translation.ts`:

```typescript
// app/config/translation.ts
import { defineTranslationConfig } from "gemi/i18n";
import type { HttpRequest } from "gemi/http";

export default defineTranslationConfig({
  defaultLocale: "en-US",
  supportedLocales: ["en-US", "tr-TR"],

  detectLocale(req: HttpRequest) {
    return req.cookies.get("i18n-locale") ?? null;
  },

  onLocaleChange(locale: string) {
    console.log(`Locale changed to ${locale}`);
  },
});
```

Dictionaries are not listed here. `supportedLocales` is what switches locale detection on.

Register the slice on your kernel under the `translation` key:

```typescript
// app/kernel/Kernel.ts
import { Kernel } from "gemi/kernel";
import translation from "../config/translation";

export default class extends Kernel {
  config = { translation /* ...other slices */ };
}
```

`defineTranslationConfig` is an identity helper — it exists purely to type the object as `TranslationConfig`. The framework's `TranslationServiceProvider` reads this slice at boot and binds a `Translator` into the container; you never construct or subclass anything.

Configuration fields:

- **`defaultLocale`** — fallback locale (default `"en-US"`).
- **`supportedLocales`** — `string[]` of accepted locale codes (default `[]`). A requested locale outside this list falls back to `defaultLocale`. Leaving it empty switches locale detection off entirely.
- **`detectLocale(req)`** — resolve the locale for a request. Return a locale string or `null` to fall back to gemi's own detection. A typical implementation reads the `i18n-locale` cookie, then the `x-locale`/`accept-language` headers.
- **`onLocaleChange(locale)`** — hook called when the active locale changes.
- **`prefetch`**, **`components`** — deprecated; see [Legacy dictionaries](#legacy-dictionaries).

> **Note:** `detectLocale` and `onLocaleChange` are **config callbacks**, not provider methods. This is a deliberate divergence from Laravel, where such hooks are often wired inside a provider's `boot()`. In gemi every subsystem hook (`detectLocale`, `onLocaleChange`, `filterRecipients`, `onLogCreated`, …) is a plain function on its config slice, so the whole behaviour of a subsystem is readable in one file and a provider is only ever needed to bind a *new* service.

## Client usage

### `useDictionary`

`useDictionary(dictionary)` returns a translator `t` bound to that dictionary and the current locale:

```tsx
import { useDictionary } from "gemi/client";
import { homeDict } from "./Home.i18n";

function Home() {
  const t = useDictionary(homeDict);
  return <h1>{t("title", { version: "1.0" })}</h1>;
}
```

- `t(key, params?)` — the translated string for `key` in the current locale, with `params` interpolated. Params are required only when the string has placeholders.
- `t.jsx(key, params?)` — same, but typed to return a JSX element (use it when a param renders JSX, e.g. an embedded link).

If a key can't be resolved, `t` logs a warning and returns the key itself, so the UI degrades rather than crashing.

### `useLocale`

`useLocale()` returns the current locale and a setter:

```tsx
import { useLocale } from "gemi/client";

function LocaleSwitcher() {
  const [locale, setLocale] = useLocale();

  return (
    <select value={locale} onChange={(e) => setLocale(e.target.value)}>
      <option value="en-US">English</option>
      <option value="tr-TR">Türkçe</option>
    </select>
  );
}
```

`setLocale(locale)` persists the choice in the `i18n-locale` cookie and re-navigates so the new locale's dictionaries load.

## Server-side translation

### `Lang` facade

Use the [`Lang`](./facades.md) facade to read the request's locale on the server. Like every gemi facade, `Lang` is a static proxy: each call resolves the `Translator` service out of the container and forwards to it.

```typescript
import { Lang } from "gemi/facades";

const locale = Lang.locale(); // active locale for this request
Lang.getDefaultLocale();
Lang.getSupportedLocales();
Lang.setLocale("tr-TR"); // validates against supportedLocales, sets the cookie
```

If you need the underlying service directly — to inject it, or to avoid the facade in a test — resolve it yourself:

```typescript
import { app } from "gemi/foundation";
import { Translator } from "gemi/i18n";

const translator = app(Translator); // typed Translator, no cast
```

### `translate`

To read a `defineDictionary` dictionary outside React — a controller, a job, an email template — use `translate`:

```typescript
import { translate } from "gemi/i18n";
import { homeDict } from "@/app/views/Home.i18n";

const title = await translate(homeDict, "title", { params: { version: "1.0" } });
const turkish = await translate(homeDict, "title", {
  locale: "tr-TR",
  params: { version: "1.0" },
});
```

It is `async` because a bundled dictionary loads its locale on demand. Server code does not go through the bundler, so in practice it resolves without ever yielding — the `await` is what makes the same call work either way. The locale defaults to `Lang.locale()`.

### `Dictionary.text` and `Dictionary` render helpers

For strings that live on the server (validation messages, emails, generated content), translate inline without a client dictionary:

```typescript
import { Dictionary } from "gemi/i18n";

// Inline locale map -> string in the current (or given) locale
const message = Dictionary.text({
  "en-US": "Slot name is required",
  "tr-TR": "Slot adı gereklidir",
});
```

`Dictionary.text(content, args?)` picks `content[locale]` (defaulting to `Lang.locale()`), interpolating `args.params`. This is common in `HttpRequest` validation schemas:

```typescript
class CreateSlotRequest extends HttpRequest<CreateSlotInput> {
  schema = {
    name: {
      required: Dictionary.text({
        "en-US": "Slot name is required",
        "tr-TR": "Slot adı gereklidir",
      }),
    },
  };
}
```

An instance dictionary also offers **server-only** helpers:

- `dictionary.render(key, { locale?, params? })` — resolve a single key to a string in the given (or current) locale, with interpolation.
- `dictionary.reference(key)` — return the full per-locale map for a key.

> **Note:** `render` and `reference` throw if called in the browser — they are server-only. On the client, use `useTranslator`.

## Locale in emails

Emails render outside the browser, so pass the resolved locale into the email component explicitly and use it to select strings. `Dictionary.text` works here too — pass the target `locale` in its args (it otherwise defaults to `Lang.locale()`):

```tsx
import { Lang } from "gemi/facades";
import { Dictionary } from "gemi/i18n";

// When dispatching the email
sendPinEmail({ locale: Lang.locale(), pin });

// Inside the email component
function PinEmail({ locale, pin }: { locale: string; pin: string }) {
  const heading = Dictionary.text(
    { "en-US": "Your login code", "tr-TR": "Giriş kodunuz" },
    { locale },
  );
  return <Layout locale={locale}>{heading}: {pin}</Layout>;
}
```

See [Email](./email.md) for building and sending emails.

## Legacy dictionaries

`Dictionary.create` and `useTranslator` are **deprecated** but still fully supported — both APIs work side by side, so an app migrates one dictionary at a time. New code should use `defineDictionary` and `useDictionary`.

The old shape has three moving parts per dictionary instead of one:

```typescript
// 1. app/i18n/HomePage.ts — the dictionary, with a name string
import { Dictionary } from "gemi/i18n";

export const HomePage = Dictionary.create("HomePage", {
  title: { "en-US": "Welcome", "tr-TR": "Hoş geldiniz" },
});
```

```typescript
// 2. app/i18n/index.ts — every dictionary re-exported
export default { HomePage, About, Footer, Header };
```

```typescript
// 3. app/config/translation.ts — which route needs which dictionary
prefetch: {
  "/": [components.HomePage, components.Header, components.Footer],
},
```

```tsx
// and the name string again at the call site
const t = useTranslator("HomePage");
```

Plus a `gemi.d.ts` declaration to give `useTranslator` its types:

```typescript
declare module "gemi/client" {
  export interface I18nDictionary extends CreateI18nDictionary<typeof I18nComponents> {}
}
```

Why it is being replaced:

- **The `prefetch` map is written by hand and drifts.** Nothing checks it, and the only symptom of getting it wrong is a missing string at runtime.
- **The dictionaries are far from the components.** `app/i18n/` grows into thousands of lines that no longer resemble the UI they serve.
- **Everything is held in memory.** `Translator` materializes the full locale × route × dictionary × key cross-product at boot, for the life of the process.
- **The name string can drift from the identifier** in either direction, with no type error.

To migrate a dictionary: move it next to its component as `defineDictionary({...})` (dropping the name argument), swap `useTranslator("Name")` for `useDictionary(dict)`, and delete its entries from `app/i18n/index.ts` and the `prefetch` map. The interpolation syntax is unchanged, so the strings themselves move verbatim.
